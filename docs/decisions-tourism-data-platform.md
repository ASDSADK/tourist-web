# 智慧旅游网页与 UE 数据互通：技术选型

日期：2026-10-14

## 已确认的目标和决定

景区使用 UE 数字孪生软件，互联网游客通过网页查看今日进出人数、客流曲线、景点预约情况、天气和文旅资讯，以辅助安排游玩时间。

用户选定方案 B：前端采用 Vue 3、TypeScript、ECharts；后端采用 Node.js、Fastify；数据库采用 PostgreSQL。选择原因是业务模块会持续扩展，需要将页面组件、数据访问和业务统计分开维护。后端初期采用单个应用。

选型已确认；本文记录重构方向，不代表依赖已安装、功能已实现或 UE 接入已验证。

## 建议的第一版范围（待确认）

- 游客页面：景区状态、今日累计进出、当前在园人数、客流历史曲线、预约余量、天气和资讯；适配手机。
- 数据服务：接收景区端上报、校验并保存数据、统一汇总口径，提供公众查询接口和 SSE 更新。
- UE 接入：优先通过 HTTPS 上报 JSON；具体实现取决于 UE 版本、蓝图/C++结构及数据来源。
- 资讯管理：工作人员登录后发布公告与资讯，记录来源、发布时间和生效/失效时间。
- 预约先建议展示现有系统的余量并跳转官方渠道。网页直接预约、支付及订单功能尚未纳入已确认范围。
- 浏览器展示 UE 三维画面、远程控制 UE 和客流预测尚未纳入已确认范围。

## 数据归属与可靠性

UE 可在第一阶段作为上报端；如已有闸机、票务或采集服务，长期优先让 UE 与网页共享业务数据源。天气由后端对接数据源并缓存，资讯通过管理后台发布，预约优先接入已有预约系统。

上报协议需明确景区/景点 ID、数据源、采集时间、统计日期、序号或唯一标识、进出统计与在园统计的含义。区分人数与人次，统一时区及跨日规则，不将不同时间粒度的值混入同一条曲线。

上报端持有私有凭据；公众接口仅返回可公开的汇总信息。重复和乱序上报不能重复计数或覆盖较新状态。服务保存历史与最近有效快照；UE 停机或断网时，网页明确显示数据过期和最后更新时间，缺失数据不视为零，不使用模拟值替代真实值。

## 实施顺序与验收方向

1. 确认数据来源与部署条件，确定上报/查询协议及统计口径。
2. 用单个景区贯通 UE → 数据服务 → 游客网页，保存历史数据。
3. 将现有视觉风格迁移为 Vue 组件，接入预约展示、天气和资讯。
4. 验证重复上报、乱序、跨日、断线恢复、数据过期，以及 UE 关闭后的网页可访问性。

现有 HTML 是模拟演示，保留作为迁移参考。未经另行确定，不安装依赖、覆盖现有页面或部署发布。

## 待确认事项

- UE 版本，主要使用蓝图还是 C++，目前客流来自真实设备/系统还是模拟。
- 是否已有预约系统及接口，第一版仅展示预约情况还是提供直接预约。
- 演示验收还是实际上线，已有服务器、主要访问地区及预计同时在线人数。
